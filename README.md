# TripGo — Trip Service

Учебный HTTP-сервис управления поездками на Go. В первой лабораторной работе
сервис создаёт поездки, возвращает их по идентификатору и завершает; данные
хранятся в PostgreSQL.

## Требования

- Go версии из `go.mod` или новее.
- PostgreSQL, доступный по `DATABASE_URL`.
- Утилита [`goose`](https://github.com/pressly/goose) в `PATH` для миграций.

Для окружения курса используйте `tripgoctl`: скопируйте `environment.toml` в
репозиторий и следуйте
[инструкции курса по окружению](https://github.com/course-go-autumn-2026/course/blob/main/homework/docs/environment.md).
В первой работе требуется компонент PostgreSQL.

## Настройка и запуск

Создайте локальный `.env` из шаблона и укажите адрес своей базы данных:

```bash
cp .env.example .env
# Отредактируйте DATABASE_URL в .env
```

`.env` и `.tripgo/` содержат локальные настройки и игнорируются Git. Не
коммитьте в них секреты. Все обязательные для запуска параметры первой работы
должны быть заданы; сервис завершится с ошибкой, если конфигурация некорректна.

Накатите миграции и запустите сервис:

```bash
make migrate
make run
```

По умолчанию HTTP-сервер слушает `:8080`. Команда `make run ARGS=...` передаёт
дополнительные аргументы программе.

### Переменные окружения первой работы

| Переменная | Назначение |
|---|---|
| `HTTP_ADDR` | Адрес HTTP-сервера |
| `LOG_LEVEL` | Уровень логирования: `debug`, `info`, `warn` или `error` |
| `SHUTDOWN_TIMEOUT` | Бюджет времени на graceful shutdown |
| `HTTP_READ_TIMEOUT` | Максимальное время чтения запроса; по умолчанию `10s` |
| `HTTP_READ_HEADER_TIMEOUT` | Максимальное время чтения заголовков; по умолчанию `5s` |
| `HTTP_WRITE_TIMEOUT` | Максимальное время записи ответа; по умолчанию `15s` |
| `HTTP_IDLE_TIMEOUT` | Таймаут неактивного соединения; по умолчанию `60s` |
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS` | Максимальный размер пула соединений |
| `DATABASE_MIN_CONNS` | Минимальный размер пула соединений; допускается `0` |
| `DATABASE_MAX_CONN_LIFETIME` | Максимальное время жизни соединения |
| `DATABASE_CONNECT_TIMEOUT` | Таймаут установки соединения и проверки БД |
| `DATABASE_QUERY_TIMEOUT` | Таймаут запросов и транзакций |

Шаблон `.env.example` также содержит параметры последующих лабораторных работ.
В первой работе сервис использует перечисленные выше настройки.

## HTTP API

Контракт OpenAPI находится в
[`contracts/openapi/trip-service.openapi.yaml`](contracts/openapi/trip-service.openapi.yaml).
Сгенерированные типы и интерфейсы сервера находятся в
[`internal/generated/api.gen.go`](internal/generated/api.gen.go); не редактируйте
сгенерированный файл вручную.

| Метод и путь | Назначение | Основные ответы |
|---|---|---|
| `GET /health` | Проверка, что процесс работает; к БД не обращается | `200` |
| `GET /ready` | Проверка доступности PostgreSQL | `200`, `503` |
| `POST /api/v1/trips` | Создание активной поездки | `201`, `400`, `409`, `500` |
| `GET /api/v1/trips/{tripId}` | Получение поездки по UUID | `200`, `400`, `404`, `500` |
| `POST /api/v1/trips/{tripId}/finish` | Завершение активной поездки | `200`, `400`, `404`, `409`, `500` |

Успешные ответы с поездкой имеют `Content-Type: application/json`. Ошибки
возвращаются в формате RFC 9457 с `Content-Type: application/problem+json`;
машиночитаемые коды включают `invalid_request`, `trip_not_found`,
`trip_completed`, `driver_busy` и `internal_error`.

Пример создания:

```bash
curl -i http://localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -d '{
    "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
    "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
    "start_point": {"latitude": 59.9398, "longitude": 30.3146},
    "end_point": {"latitude": 59.9290, "longitude": 30.3626},
    "price": 1450
  }'
```

Цена задаётся целым числом рублей. Идентификатор генерирует сервис. Запрос
отклоняется, если в нём отсутствуют обязательные поля, есть неизвестные поля,
недопустимые UUID или координаты либо отрицательная цена.

## Решения по реализации

### Транзакции и изоляция

Менеджер транзакций открывает PostgreSQL-транзакцию, передаёт её через контекст
и выполняет callback. Репозиторий берёт executor из контекста: при наличии
транзакции использует её, иначе выполняет запрос через пул. Ошибка callback
приводит к `ROLLBACK`, успех — к `COMMIT`; вложенный `Do` использует текущую
транзакцию.

Создание поездки атомарно добавляет запись в `trips` и начальный переход в
`trip_status_history`. Завершение поездки в той же транзакции обновляет её
статус и записывает переход `active → completed`. Поэтому ошибка при записи
истории откатывает изменение поездки.

Уровень изоляции — PostgreSQL `Read Committed`, заданный при открытии
транзакции. Для этих операций целостность обеспечивают ограничения БД и
условное обновление, поэтому более строгий уровень не требуется.

### Запрет нескольких активных поездок у водителя

Миграция создаёт частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX trips_driver_active_idx
    ON trips (driver_id)
    WHERE status = 'active';
```

Индекс применяется только к активным поездкам: у водителя могут быть
завершённые поездки, но не может быть двух активных. Это ограничение
обеспечивается PostgreSQL, а не предварительным `SELECT` в приложении, поэтому
сохраняется и при одновременных запросах. Нарушение именно этого индекса
распознаётся по коду PostgreSQL `23505` и преобразуется в `409 driver_busy`.

Завершение защищено условием `WHERE status = 'active'` в `UPDATE`. При двух
конкурентных запросах только один может изменить поездку; повторное завершение
возвращает `409 trip_completed`, а `finished_at` не перезаписывается.

## Миграции и проверки

```bash
make migrate       # применить все новые миграции
make migrate-down  # откатить одну последнюю миграцию
make generate      # перегенерировать OpenAPI-код
make test          # go test -race и сводка покрытия
make lint          # golangci-lint
```

Две миграции нужно откатывать по одной: первый `make migrate-down` удаляет
`trip_status_history`, следующий — `trips`. `make test-integration` запускает
тесты с build tag `integration`. На данный момент специальных интеграционных
тестов с этим тегом в репозитории нет; `make test` запускает существующие
автоматические тесты с `-race`.

Для ручной проверки конкурентности можно отправить несколько запросов
создания с одинаковым `driver_id`: ожидается один успешный ответ `201`, а
остальные запросы при конфликте получат `409 driver_busy`. Для проверки
атомарности временно вызовите ошибку при вставке истории и убедитесь, что
вставка поездки также откатилась.

## Структура проекта

```text
cmd/trip-service/       запуск сервиса и сборка зависимостей
contracts/openapi/      исходный HTTP-контракт
internal/generated/     сгенерированный OpenAPI-код
internal/config/        чтение и проверка конфигурации
internal/domain/        правила и ошибки домена
internal/http/          HTTP-обработчики и middleware
internal/infra/         PostgreSQL-транзакции и telemetry
internal/model/         модели данных между слоями
internal/repository/    PostgreSQL-репозитории
internal/usecase/       сценарии создания, получения и завершения поездок
migrations/             миграции goose
```
